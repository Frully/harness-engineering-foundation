# Harness Engineering Foundation

[English README](./README.md)

这是一个可运行的参考项目，展示在 AI 驱动开发中，如何防止产品在持续变更下逐步失控。

项目包含后端、Web 端、移动端三个端和一套围绕它们的控制层。控制层通过架构检查、自动化测试、冒烟验证和界面审查，确保 AI 每次改动都不会破坏已有的结构、行为和设计。它提供的是一个可持续改进的架构基础，而不是一个最终方案。

## 要解决的问题

当 AI 成为主要实现者时，不能只靠人的记忆和评审经验来维持一致性。AI 可以快速修改大量文件，也可以反复犯同一种结构性错误。如果项目没有把关键边界写成能自动检查的规则，常见问题会迅速累积：

- 代码放进错误的位置，各端之间的边界混淆
- 底层模块反向依赖了上层模块
- 测试停留在浅层验证或走过场的冒烟测试
- “完成”的定义因人、因 AI、因 CI 而不同
- 界面文案和设计逐步跑偏，即使代码仍然能编译
- 关键知识停留在聊天上下文里，无法沉淀为项目知识

**Harness Engineering** 就是围绕产品建立一层明确的控制层来解决这个问题。

## 项目结构

| 目录 | 职责 |
|------|------|
| `workspace/` | 只放产品代码。后端、Web 端、移动端明确分离。 |
| `harness/` | 控制层：规则、自动化检查、共享脚本。 |
| `docs/` | 需要长期保留的项目知识：系统行为、对外接口契约、设计规范。 |
| `deploy/` | 部署资产和发布基础设施。 |

改 `workspace/` 是改产品。改 `harness/` 是改产品周围的约束。改 `docs/` 是维护未来 AI 也必须读取的稳定知识。当某个行为、契约或设计决策变成稳定结论时，应该从聊天记录或代码注释中提取出来，写进 `docs/`，防止知识随对话消失。

## 约束了什么

控制层的约束分两层。**弱约束**是文本规则（`harness/AGENTS.md`、`harness/rules/`），AI 在改动前读取，尽量不出错。**强约束**是自动化检查脚本，AI 出错后无法通过检查。弱约束降低出错概率，强约束兜底拦截。

### 架构检查

Harness 读取各端的依赖清单（`go.mod`、`package.json`、`pubspec.yaml`），在此基础上确保各层之间的依赖方向正确、阻止各端之间互相引用、检查代码是否放在了正确的位置。

### 各端自身的检查入口

除了 harness 层面的架构检查，每个端还有三个自身的检查入口：

| 入口 | 职责 |
|------|------|
| `check.sh` | 快速质量关卡：格式化、lint、类型检查、静态分析、能否正常构建。 |
| `test.sh` | 功能验证：单元、组件、widget、集成或 API 测试。 |
| `smoke.sh` | 启动真实服务，端到端跑通完整的基线业务流程。 |

项目级最终质量关卡统一串联以上所有检查：

```bash
bash harness/scripts/verify.sh
```

### 界面也是工程约束

控制层还约束统一的界面设计规范和文案标准、Web 端作为视觉基准、移动端对齐同一套规范，以及新增或明显修改界面时的截图审查。技术上正确但视觉跑偏的界面不算通过。

## 人的角色

人不应该是在流水线末端逐个修补 AI 的错误。更高效的做法是：

1. 识别重复出现的失败模式。
2. 判断哪些问题应该沉淀成规则、检查、工作流或文档。
3. 通过 AI 在 `workspace/`、`harness/` 和 `docs/` 中落地这些改进。

没有一开始就完美的控制层。Harness 的价值不在于一次性挡住所有问题，而在于每次发现新的失败模式时，都能把它编码成规则或检查，让同类问题不再复现。改进 harness 不是附带工作，而是开发工作本身的核心部分。

## 当前演示基线

当前可运行的基线是一条小型认证流程，覆盖注册、登录、登出和会话恢复。它的作用是给 harness 提供一条贯穿多端的真实业务流程来验证。

## 动手试试

理解 harness 最好的方式是让 AI 在里面工作，然后观察控制层如何约束结果。把项目 clone 下来，用你习惯的 AI 编程工具打开，然后把下面的提示词交给它，观察弱约束如何引导它的选择、强约束如何拦截它的错误。

### 开发一个功能

当前基线只有认证流程。试着扩展它：

> 加一个"注销账户"功能。后端需要吊销该用户的所有会话并永久删除用户数据。Web 端和移动端都需要一个确认对话框，让用户感受到这个操作不可撤销。

Harness 会在整个过程中约束代码位置、分层依赖、测试覆盖和界面文案标准。如果 AI 把处理逻辑放进了错误的层或跳过了测试，`verify.sh` 会拒绝它。

### 改进一条约束

当前 harness 没有任何 git commit 相关的约束。AI 提交代码时可以写任意格式的 commit message，没有规则约束内容和格式。试着补上这个缺口：

> 项目目前没有 commit message 规范。添加一条 harness 约束，要求 commit message 遵循 conventional commits 格式，并通过 git hook 自动检查。不符合格式的提交应该被拒绝。
